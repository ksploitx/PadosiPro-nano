# DESIGN — padosipro-nano

## Stack

- **Backend:** FastAPI (async), SQLite (single file DB, no container), Redis (OTP cooldown only), JWT auth, bcrypt for password + OTP hashing. Mailpit as the local SMTP catcher.
- **Mobile:** Flutter, Provider for state, `flutter_secure_storage` for the JWT, plain `http` package (no codegen).

Reasoning: both are stacks you already know (FastAPI, SQLite, Redis, Flutter are on your stated stack), and this v1 keeps the data layer simple by using a single SQLite file instead of a separate database service. That lets the rebuild stay focused on the product requirements rather than spinning up extra infrastructure mid-assignment.

## Key decisions

1. **OTP logic isolated as pure functions.** `evaluate_otp_attempt()` takes primitives in, returns an outcome enum. No DB session, no async. This is what gets unit tested first, before any endpoint exists — it's the highest-weighted risky logic in the brief.
2. **`GET /profile` returning 404 is the source of truth for "has this user finished onboarding," not a boolean cached on the client.** Avoids a stale flag if the user finishes profile on a different device or a request fails mid-way.
3. **Task selection uses POST/PATCH/DELETE endpoints.** Replaces the older full-replace PUT to allow individual task modifications (requested_time and note).
4. **Business Name is optional.** Not every household running tasks through the app is a registered business.
5. **Redis is scoped to exactly one job: the resend cooldown.** Everything else (OTP state, attempts) lives in SQLite because it needs to survive and be queryable, not just expire.
6. **SQLite is a plain file, not a containerized database service.** The app keeps one local database file and avoids the extra operational complexity of a separate DB container in this v1.

## Testing strategy

- Unit tests on `otp.py` first (generation length/randomness, hash roundtrip, expiry boundary, attempt-limit boundary, and every branch of `evaluate_otp_attempt`).
- Integration tests on the four auth endpoints against a real test DB (happy path + the specific failure modes: wrong code, expired code, too many attempts, unverified login).
- Flutter: widget test on the OTP screen's countdown/error states at minimum.

## Known trade-offs (carried forward intentionally, not oversights)

- No refresh tokens — a single JWT with a generous expiry.
- No rate limiting per IP.
- No migrations tool for v1 (`create_all` at startup) — add Alembic before this goes anywhere near production.
- CORS wide open — dev only.
- Single-writer limitation — only one process should write to the SQLite file at a time.

## Definition of done (per module)

- Backend module: endpoint implemented, server-side validation matches HLD, at least one test, tried against a live curl/Postman call (not just read).
- Mobile screen: matches HLD's states (loading/error/empty), wired to the real backend (not a mock), tried on an emulator.
